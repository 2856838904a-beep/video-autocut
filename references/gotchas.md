# 踩过的坑(全部实测,按代价排序)

## 0. 单机 3A 故事剪辑:过场黑边是核心信号(荒野大镖客实测)

**背景**:单机 3A 的"故事"不在解说密度里,而在剧情演出本身。这类游戏(大镖客、GTA 等)的过场动画有稳定的画面特征 —— **电影黑边**:

```
正常游玩  crop=1920:1080:0:0      满幅
过场动画  crop=1920:816:0:132     上下各 132 像素黑边
```

**实测有效性**:10 个文件 / 17.4 小时 → 检测出 **295 段过场 / 166 分钟**(占素材 16%)。判据极干净,是故事剪辑最可靠的骨架。

**⚠️ 不要用 ffmpeg 的 `cropdetect` 实现(踩了两个坑)**:
1. **`cropdetect` 在检测值稳定后会静默** —— 不再逐帧打印,除非每帧强制 `reset`。
   实测 45 分钟素材只拿到 **28 行**,而不是预期的 2700 行。
2. **它的日志里同时有 `pts:N` 和 `t:X` 两个数字字段**,用 `t:([\d.]+)` 之类的正则很容易
   误匹配 `pts:`(实测就踩了,导致时间戳全错)。

**正确做法**:自己解码灰度帧(`ffmpeg ... -vf fps=1,scale=320:180,format=gray -f rawvideo -`),
直接测上下边缘的暗像素行数。更快、更准、不依赖过滤器的打印行为。
见 `scripts/detect_cutscenes.py`。

**补一条**:只靠黑边会漏掉**触发在游玩中的剧情演出**(没有黑边)。实测某文件原片
62:41 处有 *"Where's my goddamn son? Where is he?"* —— 剧情高潮,但没有黑边。
所以还需要转写**游戏对白轨**(英文)按对白密度补捞。见 `scripts/rdr_compose.py`。

## 0b. 单机 3A 的音频结构与联机完全不同

**大镖客实测**(与 MC 那批对比):

| 轨 | RMS | 内容 |
|---|---|---|
| 轨1 / 轨4 | -31~-45 dB | **游戏原声**(音效+配乐+剧情对白,全英文),轨1 与轨4 近似副本 |
| 轨2 | **-85 dB** | 玩家解说(极轻) |
| 轨3 | **-70 dB** | 玩家解说(稍响) |

**两个要点**:
1. **解说可能被录得极轻**(轨道间差 70~85 dB)。这时它不适合做主音轨,但**可以作为
   "参考轨"单独铺一条音频轨**放在剪映时间线上 —— 便于对照,不混入主音轨。
   实现见 `make_draft.py --extra-audio`。
2. **不能用"中文字密度"单独挑轨** —— 单机游戏的解说更稀疏,且游戏原声里有大量英文对白。
   判据要区分语言:en 且高能量 = 游戏原声;zh = 解说。

## 0c. 音轨结构不对 → 剪映**静默丢弃整条音轨**(2026-09 实测,代价极高)⚠️

**现象**:草稿 JSON 里明明有 `video` + `audio` 两条轨,`draft_info.json` 的段、
素材、文件路径全部正确校验通过,但剪映打开后**只有一条轨**,而且**不报任何错**。
用户会说"没有两条轨道",你却在数据里找不到问题 —— 极易误判成"用户看错了"。

**根因**:`materials.audios[]` 相关结构有 3 处非法,剪映解析素材失败后把整轨丢掉。
对照剪映自己产出的明文草稿(本机 `2月11日` 系列,含真实 audio 轨)可看出:

| 项 | 剪映真实草稿 | 出错时的写法 |
|---|---|---|
| `materials.audios[].type` | `music` / `text_to_audio` | ❌ `"audio"`(**不是合法值**) |
| 段 `extra_material_refs` | 4 个引用 | ❌ `[]` |
| 音频段字段数 | 44 | ❌ 9 |

**三条硬规则**:

1. `materials.audios[].type` 只能是 `music`(本地导入音频)/ `text_to_audio` /
   `record` / `extract_music`。`"audio"` 会让剪映解析失败。
2. **每个片段都必须通过 `extra_material_refs` 引用一个 `speeds` 素材**
   (实测真实草稿 `speeds` 数量 == 片段总数)。音频段还要 `beats`。
   音频段的标准引用是 `[speeds, beats, sound_channel_mappings, vocal_separations]`。
3. 音频段必须写**完整 44 字段**,不能只给 9 字段的最小版。

**辅助素材模板**(照抄即可,值不重要,存在与引用才重要):

```json
// materials.speeds[]         speed 必须 1.0(不然会变速)
{"id":"...","type":"speed","mode":0,"speed":1.0,"curve_speed":null}
// materials.sound_channel_mappings[]
{"id":"...","type":"sound_channel_mapping","audio_channel_mapping":0,"is_config_open":false}
// materials.vocal_separations[]
{"id":"...","type":"vocal_separation","choice":0,"production_path":"","time_range":null,"removed_sounds":[]}
// materials.beats[]
{"id":"...","type":"beats","enable_ai_beats":false,"gear":404,"gear_count":0,"mode":404,
 "user_delete_ai_beats":null,"ai_beats":{"melody_url":"","melody_path":"","beats_url":"",
 "beats_path":"","melody_percents":[0.6],"beat_speed_infos":[]},"user_beats":[]}
```

**已有草稿的补救**:`scripts/fix_audio_track.py <草稿目录> [--also-content]`
就地修复(自动备份到 `.backup_<时间戳>/`)。`make_draft.py` 已按上述规则产出,
新草稿不会再犯。

**排查这类"数据对、剪映不认"问题的方法**:库里有剪映自己的明文草稿时,
**先 diff 结构再怀疑数据**。本机 `.../com.lveditor.draft/` 下除自建草稿外
还有几十个真人草稿(如 `2月11日 (1)~(6)`),它们是**唯一可信的标准答案**。
注意用 `os.listdir` 枚举 —— 它们大多没有 `draft_info.json`,只用
`glob('*')` + 判 `draft_info.json` 存在会把它们全部漏掉。

## 1. OBS 有 4 条音轨,而且**不能用能量判据挑解说轨** ⚠️ 最贵

**现象**:按默认抽音轨(`-vn -ac 1`)得到 44 小时里"28.6 小时几乎无声",据此差点得出"大部分录像没录到声音"的错误结论。

**真相**:OBS 分轨录制的 MKV 里有 **4 条独立音轨**(`simple_aac_recording0..3`)。默认只取第一条,常常是游戏声。而且**每条素材的解说轨位置不一样**(轨1/2/3/4 都出现过),不能写死。

**更深一层的坑(踩了两次)**:即使逐轨测了,也**不能用音频能量活跃度(>-35dB 时间占比)挑解说轨**。实测反例:

```
2026-07-05_10-17-40.mkv   轨1 能量 100%  →  转写语言 en,中文字 0    ← 纯游戏音效
                          轨3 能量  54%  →  中文 49.6 字/分钟       ← 真正的解说
2026-07-04_13-45-54.mkv   轨1(能量最高) →  0 字/分
                          轨2            →  73.5 字/分
```

**能量只说明"有声音",不说明"有解说"** —— 游戏音效常常比人声更响。
全库 17 个文件用能量判据挑轨,**9 个挑错(53%)**,其中 4 个错到"转写 0 字/分"。
规律:正确轨多数是**轨2**,而能量判据总挑轨1或轨4。

**⚠️ 不要用"取最大值代替平均值"来加强能量判据** —— 那会放大这个错误(某段音效爆发就把整条轨选上)。这是本项目走过的一次弯路,已在 `extract_audio.py` 里留注释警告。

**正确做法**:
1. 能量粗筛候选(按能量排序前 2 + 所有能量 >25% 的轨)
2. 对候选轨抽 3×40 秒样本,**用 faster-whisper 快速转写**
3. 按「中文字/分钟」定胜负 —— **ASR 是唯一可靠的鉴别器**,它本来就是为识别语音设计的

`scripts/extract_audio.py --track auto` 已实现这套。独立的逐轨验证器见
`scripts/verify_tracks_all.py`(全库 17 文件约 15 分钟出对照表)。

**快速自检判据**:某文件转写句数远少于时长(如 6 小时只有 75 句、2 小时只有 1 句)就是轨挑错了。正常每小时应有几百句。

## 2. 长音轨一次性转写会 MemoryError

**现象**:6 小时音轨直接喂 faster-whisper → `MemoryError`(不是显存不足,系统 47 GB 内存只剩 21 GB 也会爆)。

**原因**:VAD + 词级对齐要在内存里铺开整段音频。

**做法**:切 20 分钟块分别转写,时间轴平移后合并。内存占用恒定,模型只加载一次,每块落盘可断点续跑。见 `scripts/transcribe_long.py`。

**附带收益**:单块失败不会毁掉整条任务。

## 3. 选段单元用"单句爆点 + 时间窗口"会把对话剁碎

**现象**:用户反馈"对话完整性还是差了一些"。量化后:10 个切点里 **5 个紧贴前后文**(间隔 <1.5 秒),即正在说话就被截断;11 个真实对话事件里有 118 秒和 221 秒的两个被各切成 3~4 段碎片。

**根因**:窗口按**时间长度**定(前后撑 10~20 秒),不是按**对话边界**定。这个思路必然切碎对话。

**做法**:先用停顿切出完整事件,事件切分阈值**从数据里推**(停顿分布的 p93,本例 5.8 秒),整个事件作为候选单元。事件过长时,只在事件内部的呼吸口(≥3 秒停顿)细分。

**推论**:任何"在爆点周围开窗"的实现都有这个缺陷。

## 4. 打分词典必须匹配品类

**现象**:生存类素材(MC)用射击游戏词典打分,结果"情绪 1.5 的段落被选中、情绪 12 的只有 20 秒"。用户指出"这是生存类游戏"后才定位到。

**真相**:一段 118 秒的对话含 **35 处物资/交易讨论**(附魔、传说下界合金、翘翅、碎片),是全场最值钱的一段,却被判成"又长又水"——只因为没人在喊。

**做法**:生存类按六维度打分(物资交易/计划决策/探索发现/建造成就/危机冲突/情绪欢乐),见 `scoring.md`。**开口第一件事就是确认品类。**

## 5. 剪映草稿:主文件名与素材登记

**主文件名**:剪映 6.0+ 是 `draft_info.json`。写 `draft_content.json` 会报"草稿内容已损坏"。
实测(11.2.0.14339):在空目录写 `draft_info.json` + `draft_meta_info.json` 即可打开;剪映随后自己生成 `draft_content.json`(密文)、`Timelines/<id>/` 镜像、`.backup/`、封面,并把自己分配的 timeline id 写回 `draft_info.json` 的 `id` 字段。**除 id 外手写字段逐字节保留。**

**三条 ID 链(漏第二条必报"媒体丢失")**:
```
segment.material_id                    == materials.videos[i].id
materials.videos[i].local_material_id  == draft_meta_info.draft_materials[type=0].value[j].id
```
剪映的"重新链接媒体"对话框**修不好**这个错,必须生成时就写对。

**必填值**(从本机真实草稿抄,别猜):`version=400000`、`new_version="127.0.0"`、`platform.app_version` 与本机一致、35 个顶层键 + 54 个 materials 桶齐全。骨架最方便的来源是任意草稿的 `Timelines/<id>/template.tmp`(明文)。

**不要复制 seed 模板的 `Timelines/` 目录** —— 会导致"打开的是模板的空时间线"。

## 6. 剪映运行时写入会被覆盖

剪映有自动保存,外部写入会被回滚。写入前**必须完全退出主程序**(托盘进程无所谓)。
`scripts/install_when_closed.py` 轮询 `tasklist`,退出后自动安装,省掉"关掉再回来跑命令"。

## 7. 装 faster-whisper 会打断本机 protobuf 依赖

**现象**:pip 把 `protobuf` 从 3.20.3 升到 7.36.1,导致本机**掘金量化 SDK**(`gm 3.0.183`,要求 `protobuf<4.0`)的 `import gm.api` 直接失败。用户有正在跑的量化交易进程。

**修复**:`onnxruntime` 降到 1.21.1(1.20/1.21/1.22/1.23 都只写 `protobuf` 不限下限)+ `protobuf` 回 3.20.3。三方复验:`gm.api` / 转写 / torch CUDA 同时可用。

**教训**:在有生产依赖的机器上装 ML 包前,先记录关键包的版本,装完逐个复验。

## 8. 其它小坑

- **`-hwaccel cuda` 产出 0 帧**。要用 `-c:v hevc_cuvid`(或 h264_cuvid),实测快 2.61x。
- **首次 CUDA 推理极慢**(14.6s vs 之后 0.39s),是 cuBLAS/cuDNN autotune 一次性开销。流水线必须复用同一个 `WhisperModel` 实例。
- **`ffmpeg -filters` 的 `scdet` 只在切换时打印**,拿不到逐帧运动值。用解码后的灰度帧自己做差分,更快也更可控。
- **`ebur128` 的逐帧 `M:` 输出在 stderr 被重定向时会被吞掉**。自己解码 PCM 算 RMS 更可靠。
- **PowerShell 会把 python 的 stderr 当错误**,`$LASTEXITCODE=1` 但程序其实成功。别只看退出码。
- **`Measure-Command` 会吞掉被包裹命令的输出**,调试时别用——会掩盖失败(本项目就因此漏掉一次转写失败)。
- **Python docstring 里写 Windows 路径要加 `r"""`**,否则 `\M` 之类触发 `SyntaxWarning`,某些情况下直接 `SyntaxError`。
- **PowerShell 的 `Set-Content -Encoding UTF8` 会改坏文件编码**(中文变乱码)。改文件用编辑工具,别用 shell 重写。
- **`pip install torch --index-url .../cu128` 是静默 NO-OP**:已装的 `2.7.1+cpu` 满足无版本约束,pip 认为"已满足"。必须 `--force-reinstall` + 显式 `==2.7.1+cu128`。
- **download.pytorch.org 只有 0.8 MB/s**(cu128 wheel 有 3.1 GB)。用 `mirror.sjtu.edu.cn/pytorch-wheels/cu128/`,实测 39~45 MB/s。

## 0d. 负时长片段:会静默丢片段(2026-11 影之刃实战)

**现象**:草稿里少了一段,`cut_clips.py` 只在终端打一行 FAIL,不细看根本发现不了。

**根因**:`pick.py` 补边+去重时,同一时间段的两段在补 `--pad` 后重叠,
把后一段的 `start` 推到前一段的 `end` 之后 —— 若超过自己的 `end`,就得到
`start > end` 的负时长段。ffmpeg 对负时长直接报错。

**修法**:去重时加一条「`end - start < 1.0` 就丢弃」;`cut_clips.py` 再加一层
防御(跳过 `dur <= 0.5` 并告警)。**排查时先扫 `dur<=0` 的段**:

```python
bad = [c for c in cuts if c["end"] - c["start"] <= 0]
```

## 0e. 稀疏对白素材:whisper 会把句子拉长(同批次发现)

动作游戏只有过场才有台词,whisper 会把一小句台词标记成跨几分钟 ——
实测「3 个词跨 402 秒」、单句最长 931 秒。不规整会让选段出现 181s/491s 的
怪物候选。统一走 `transcript.py`(按字数反推时长上界裁剪),别再直接 `json.load`。

## 0f. `--final-root` 传成「根/名字」→ 素材路径多一层(2026-11 影之刃实战)

**现象**:草稿能装进库、剪映里能看到,但打开一片"媒体丢失",或者干脆打不开。

**根因**:`make_draft.py` 内部 `path_folder = join(final_root, name)` ——
所以 `--final-root` 要传**草稿库根目录**,脚本自己拼草稿名。传成
`<库根>/影之刃 EP01` 就会写出 `<库根>/影之刃 EP01/影之刃 EP01/_media/...`,
实测 6 个草稿 136~226 条素材路径全部不可达。

**修法**:
- 现在 `make_draft.py` 会直接拒绝这种情况并提示"应传 XXX";
- 已生成的草稿可以用字符串收敛救回来(把 `<名>/<名>/` → `<名>/`),
  见本批次 `fix_draft_paths.py`;改完用 `validate_draft.py` 复查(应 0 不可达)。

**判据**:`validate_draft.py` 报 `PASS` 且没有"素材尚不可达"列表。

## 0g. 固定时长切分会毁掉连续性(2026-11 影之刃实战)

**现象**:用户反馈"剪的太碎了,连续性有问题"。量化:一集 13 分钟 **96 个片段**,
中位段长 **6.8 秒**,段间跳变 53 处超过 1 分钟(最长 39.8 分钟)。

**根因有两层**:① `pick.py` 按价值峰值选段,天然是 6~30 秒的小段;
② `tighten.py` 又按句子把它切得更碎。两者叠加 = 跳剪合集。

**错误修法**:把每段"拉长到固定 90 秒" —— 方向对了一半,但镜头长度应由内容决定,
统一 90 秒会切碎长战斗、又给短对白凑尾巴。

**正确修法**:按「叙事节拍」切并选(`beats.py`):对白停顿 >=2s、张力连续 >=5s 低于
p30、文件边界作为节拍边界;节拍长度天然 20 秒~5 分钟不等;再按"词典维度/分钟 +
张力峰值 + 起势"选节拍凑预算。

**验收指标**(别只看总时长):片段数 / 中位段长 / 段间跳变数。
